Sikumon — Technical Specification
1. Project Overview
Sikumon is a standalone Windows desktop application designed primarily for the Israeli market.
Its purpose is to process recorded Hebrew meetings and conversations through a local-first workflow:
Hebrew audio → local transcription → editable timestamped transcript → cloud text analysis → decisions and tasks → evidence-linked results → local persistence
The application must demonstrate the ability to build a complete AI-enabled desktop product specifically adapted to Hebrew-speaking users and Israeli-market requirements.
Sikumon must not look or behave like:
* a proof-of-concept;
* a developer demo;
* a chat interface wrapped around an LLM;
* a thin API client;
* a browser-based application;
* an unfinished technical prototype.
It must be a finished portfolio-quality Windows application that can be installed, launched, demonstrated, and used without a development environment.
________________


2. Product Positioning
Sikumon is a Hebrew-first local meeting assistant.
Its primary purpose is to transform recorded Hebrew meetings into structured, actionable information while keeping:
* the original audio local;
* Speech-to-Text processing local;
* transcript storage local;
* meeting data local.
Only transcript text required for AI analysis may be sent to the configured cloud LLM provider.
Core product characteristics:
* Hebrew-first UX;
* intentional RTL support;
* local Hebrew Speech-to-Text;
* no cloud audio transcription;
* local meeting storage;
* local transcript storage;
* editable timestamped transcripts;
* structured cloud AI meeting analysis;
* extraction of meeting summaries;
* extraction of decisions;
* extraction of action items;
* extraction of responsible persons only when supported by the transcript;
* extraction of deadlines only when supported by the transcript;
* evidence-linked AI results;
* persistent Windows desktop storage;
* no browser requirement;
* no NVIDIA GPU requirement.
Primary target users:
* Hebrew-speaking professionals;
* small businesses;
* consultants;
* project teams;
* project managers;
* users handling meeting recordings;
* users who want meeting summaries while keeping original recordings local.
Primary market:
* Israel.

3. Privacy Model
Sikumon's privacy model must be technically accurate.
The following remain local:
* original meeting audio;
* audio decoding;
* Speech-to-Text processing;
* transcript storage;
* transcript edits;
* SQLite database;
* meeting metadata;
* validated AI analysis stored by Sikumon.
The only meeting content that may be sent to the configured LLM provider is transcript-related text required for analysis.
The application must never send:
* source audio;
* decoded audio;
* audio fragments;
* local STT model files;
* SQLite database files;
* unrelated meetings;
* arbitrary user files.
The application must never claim that all processing is offline.
Correct product positioning:
Local Hebrew transcription and local meeting storage with optional cloud text analysis.
A more concise user-facing formulation may be:
Your audio stays on your computer. Only transcript text is sent for AI analysis.

4. Product Goal
The finished application must support the complete workflow below.
1. User installs Sikumon on Windows.
2. User launches Sikumon normally from Windows.
3. Sikumon initializes local application storage and the SQLite database if necessary.
4. User sees previously saved meetings.
5. User creates a new meeting.
6. User selects an existing Hebrew audio recording.
7. User enters or edits the meeting title.
8. Sikumon validates the selected media file.
9. Sikumon copies the source media into Sikumon's local meeting storage.
10. Sikumon creates the meeting database record.
11. Sikumon checks whether the required Hebrew transcription model is installed.
12. If the model is missing, the user is offered an in-application model download flow.
13. The model is downloaded and verified.
14. User starts transcription.
15. Sikumon transcribes the recording locally using faster-whisper and the configured Ivrit.ai model.
16. Transcription executes on the local CPU.
17. The application remains responsive.
18. Transcript segments containing stable IDs and timestamps are persisted.
19. User reviews the Hebrew transcript.
20. User corrects transcription errors segment by segment.
21. User saves corrected transcript text.
22. User starts meeting analysis.
23. Sikumon sends structured transcript text and transcript segment identifiers to the configured OpenAI text model.
24. Audio is never included in the request.
25. OpenAI returns structured analysis.
26. Sikumon validates the response using Pydantic.
27. Sikumon validates all evidence segment IDs.
28. Only a fully valid analysis becomes the current saved analysis.
29. User sees:
* meeting summary;
* decisions;
* action items;
* responsible persons when supported;
* deadlines when supported;
* transcript evidence.
30. User selects an evidence reference.
31. Sikumon navigates to the corresponding transcript segment.
32. User closes the application.
33. User launches Sikumon again.
34. Meeting data, transcript corrections, local audio reference, and analysis remain available.
35. User may edit the transcript again.
36. Existing analysis becomes visibly outdated.
37. User may rerun analysis.
38. A failed reanalysis does not destroy the previous valid analysis.
39. User may permanently delete the meeting.
40. Meeting deletion removes all local data belonging to that meeting.
This workflow must function end-to-end.

14. Model Verification Contract
A downloaded STT model is considered verified only when:
* expected model files exist;
* files are readable;
* model metadata corresponds to the configured repository/revision where available;
* faster-whisper can construct a WhisperModel from the local model directory.
A full transcription test is not required on every application startup.
Normal application startup must not load the complete STT model into RAM merely to check whether it exists.
A lightweight file/integrity check is preferred during normal startup.

19. Meeting Import Transaction
A meeting must not appear as successfully imported if copying the source recording fails.
Recommended sequence:
1. validate source;
2. allocate meeting UUID;
3. create temporary meeting directory;
4. copy source recording;
5. verify copied file;
6. create database record;
7. finalize local storage;
8. expose meeting in UI.
Failures must clean up temporary files where safe.

23. Transcript Revision
transcript_revision is the authoritative version identifier of transcript content.
The revision must increase whenever persisted transcript content changes successfully.
Examples:
* first completed transcription creates revision 1;
* user edits and saves transcript → revision 2;
* another successful edit → revision 3.
A failed save must not advance the revision.
A retranscription that successfully replaces the transcript must create a new revision.
Transcript freshness must not rely solely on timestamps.
________________

33. Transcript Save Behavior
Editing produces unsaved application state.
The UI must clearly indicate unsaved changes.
Saving transcript changes must:
1. verify meeting still exists;
2. persist changed segment text transactionally;
3. update affected segment timestamps;
4. update Meeting.transcript_updated_at;
5. increment Meeting.transcript_revision.
If saving fails:
* previous persisted transcript remains intact;
* revision does not advance.
A change in transcript revision automatically makes an older current analysis outdated through the freshness rule.

42. Analysis Prompt Requirements
The analysis instruction must explicitly require the model to:
* analyze only the supplied transcript;
* produce the summary in Hebrew;
* identify only decisions supported by the transcript;
* identify only action items supported by the transcript;
* never invent people;
* never invent deadlines;
* never invent decisions;
* never invent tasks;
* use null when an assignee cannot be established;
* use null when a deadline cannot be established;
* return empty lists when no valid items exist;
* use only supplied segment IDs for evidence;
* attach evidence to every decision;
* attach evidence to every action item;
* follow the supplied structured-output schema.
The prompt must be versioned.
Example:
ANALYSIS_PROMPT_VERSION = "1"

43. Structured Analysis Schema
Conceptual Pydantic schema:
from pydantic import BaseModel




class Evidence(BaseModel):
    segment_ids: list[str]




class Decision(BaseModel):
    title: str
    description: str | None = None
    evidence: Evidence




class ActionItem(BaseModel):
    title: str
    description: str | None = None
    assignee: str | None = None
    deadline: str | None = None
    evidence: Evidence




class MeetingAnalysisPayload(BaseModel):
    summary: str
    decisions: list[Decision]
    action_items: list[ActionItem]


The production schema may add fields where justified but must not weaken validation.
________________


44. Evidence Requirements
Every extracted decision and action item must contain at least one supporting transcript segment ID.
A result containing empty evidence for a decision or action item is invalid.
Summary text does not require per-sentence evidence in the current version.
________________


45. Evidence Validation
After Pydantic parsing, Sikumon must perform semantic evidence validation.
Each evidence segment ID must:
* exist;
* belong to the current meeting;
* belong to the transcript revision being analyzed.
Required handling:
1. receive structured response;
2. validate schema;
3. validate segment IDs;
4. if invalid, perform at most one controlled correction retry;
5. validate corrected result;
6. if still invalid, mark the analysis attempt failed;
7. preserve previous valid current analysis.
Do not silently discard invalid evidence IDs.
________________


46. Hallucination Rules
The application must prefer absent information over fabricated information.
If responsible person cannot be determined:
assignee = null


If deadline is absent:
deadline = null


If no decisions exist:
"decisions": []


If no tasks exist:
"action_items": []


The model must not convert assumptions into structured facts.
________________

49. Speaker Identification
Speaker diarization is intentionally omitted in v0.1.0 to keep local transcription lightweight and compatible with a wider range of Windows PCs, including CPU-only systems.
Adding diarization would increase model complexity, processing time, memory use, packaging complexity, and hardware requirements. This release prioritizes reliable local Hebrew STT on ordinary Windows PCs without requiring a dedicated GPU.
Do not introduce:
* pyannote;
* speaker embeddings;
* voice identification;
* external diarization API;
* speaker-recognition models;
* extra authentication requirements for diarization.
The transcript is timestamped but not automatically speaker-labelled.
________________


50. Large Transcript Handling
The application must never silently truncate a transcript.
Before analysis, the application should conservatively determine whether the transcript can be sent safely in one request to the configured analysis model.
For the initial product version:
* normal meetings are analyzed in a single request;
* automatic hierarchical/chunked analysis is not required;
* no transcript content may be silently discarded.

56. Transcription Workflow
When transcription starts:
1. verify meeting exists;
2. verify local source audio exists;
3. verify model is available;
4. prevent second transcription for the same meeting;
5. set transcription_status = RUNNING;
6. run STT in background;
7. produce ordered timestamped segments;
8. persist transcript transactionally;
9. set or increment transcript revision;
10. update transcript timestamps;
11. set transcription_status = COMPLETED.
On failure:
transcription_status = FAILED


A previous valid transcript must not be destroyed merely because a retranscription attempt failed.
________________


57. Retranscription
Retranscription is not required in the primary UI for the initial version.
If implemented:
* existing transcript must remain available until replacement transcription completes successfully;
* replacement transcript must produce a new transcript revision;
* existing analysis automatically becomes outdated;
* evidence tied to the previous transcript revision must not be treated as evidence for the new revision.
________________


58. Background Processing
The following must never execute on the PySide6 main UI thread:
* STT model download;
* STT model verification when expensive;
* perceptibly slow model loading;
* transcription;
* OpenAI network calls;
* long audio inspection/decoding.
Use appropriate Qt worker/thread mechanisms.
Worker results must be safely marshalled to the UI thread.
________________


59. Concurrency Rules
For a single meeting:
* only one transcription job may run at a time;
* only one analysis job may run at a time.
The application may globally restrict transcription to one active STT job to limit CPU and memory pressure.
Incompatible simultaneous operations must be disabled or rejected cleanly.
________________


60. Deletion During Background Work
Meeting deletion must be disabled while that meeting has an active:
* transcription operation;
* analysis operation.
The user may cancel the active operation where cancellation is supported and then delete the meeting after state normalization.
Do not implement unnecessarily complex delete-while-worker-running behavior.
________________


61. Transcription Cancellation
Transcription cancellation is required.
Cancellation must be cooperative and safe.
On cancellation:
* source audio remains intact;
* existing saved transcript remains intact;
* incomplete new transcript does not replace a valid previous transcript;
* database remains consistent.
If no previous transcript exists, the meeting returns to a clean recoverable transcription state.
________________


62. Model Download Cancellation
Model download cancellation is required.
Cancellation must:
* stop the active download;
* never mark partial data as a valid model;
* preserve or remove partial data according to a deterministic policy;
* allow clean retry.
________________


63. Analysis Workflow
Analysis sequence:
1. ensure transcript exists;
2. ensure at least one non-empty segment exists;
3. ensure OpenAI API credentials are available;
4. capture transcript_revision;
5. set analysis_operation_status = RUNNING;
6. build structured request;
7. call OpenAI Responses API;
8. receive structured response;
9. validate with Pydantic;
10. validate evidence references;
11. optionally perform one controlled correction retry;
12. persist fully valid analysis transactionally;
13. save its source_transcript_revision;
14. set it as current_analysis_id;
15. set analysis_operation_status = COMPLETED.
A partially validated analysis must never become current.
________________

* manually.

* previous valid analysis remains viewable where practical.

Failure must preserve the previous current analysis.

104. Implementation Rules for Codex
Codex must follow these rules.
1. Do not replace PySide6 with a web UI.
2. Do not introduce a backend server.
3. Do not replace local STT with cloud STT.
4. Do not send audio to OpenAI.
5. Do not replace the specified Ivrit.ai model silently.
6. Do not introduce speaker diarization.
7. Do not introduce Docker.
8. Do not require CUDA.
9. Do not introduce unnecessary infrastructure.
10. Do not introduce external database services.
11. Do not store secrets in plaintext.
12. Do not place business logic in UI widgets when it belongs in services.
13. Do not block the Qt main thread.
14. Do not treat unvalidated LLM output as application data.
15. Do not silently truncate transcripts.
16. Do not silently accept invalid evidence IDs.
17. Do not overwrite valid analysis before its replacement validates.
18. Do not destroy transcript data because a network request failed.
19. Do not expose raw Python tracebacks in normal UI.
20. Do not claim functionality is complete based only on unit tests.
21. Do not introduce out-of-scope features.
22. Prefer the simplest implementation satisfying the requirements.
23. If a specification requirement creates a technical conflict, document the conflict instead of silently changing the requirement.
24. If a dependency or model version must be changed, document why.
25. Keep third-party dependencies reasonable.
26. Do not perform broad unrelated refactors.
27. Keep behavior deterministic where correctness depends on validation or persistence.
28. Do not mark a feature complete until relevant acceptance criteria pass.
29. Do not hard-code a specific OpenAI model throughout the application.
30. Do not implement mandatory LLM chunking unless the specification is explicitly expanded.
